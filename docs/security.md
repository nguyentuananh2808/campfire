# Security

The host now applies defense-in-depth before module endpoints: HTTPS redirection and HSTS when `Security:RequireHttps=true`, `nosniff`, deny framing, no-referrer, a restrictive API Content Security Policy and `Cache-Control: no-store` for `/api/v1`. OpenAPI and Swagger routes exist only in Development. Production startup fails closed unless HTTPS is required, `AllowedHosts` is explicit and Data Protection keys have a persistent path. Forwarded host/protocol information is accepted only from the framework defaults or IP addresses explicitly listed in `ReverseProxy:KnownProxies`; do not clear the trusted-proxy lists globally.

Authentication and antiforgery cookies use `Secure=Always` whenever HTTPS is required. Invalid antiforgery tokens across every module map to the same 400 ProblemDetails response rather than becoming an unexpected 500. In-memory throttling keys use account IDs where available and otherwise use a process-rotating HMAC of the network address or guest credential, so raw IP addresses and guest cookies are not retained as limiter partition names.

The implemented Identity design is a same-origin HttpOnly ASP.NET Core Identity cookie plus an ASP.NET Core antiforgery cookie/header pair for every HTTP mutation. The readable `XSRF-TOKEN` contains only the request token; the authentication cookie and framework antiforgery cookie remain HttpOnly. Login/register/change-password are rate-limited per client IP. Password hashing, email normalization, five-attempt/15-minute lockout and security-stamp validation are owned by ASP.NET Core Identity.

Registration has no role field and assigns no role. Login failures do not disclose whether an email exists. Password changes require the current password, rotate the security stamp and refresh only the initiating session; logout deletes the current session cookie. Passwords, cookies, auth headers, antiforgery tokens, invite tokens and chat bodies are excluded from logs.

Groups authorization is server-side and resource-scoped. Non-members receive a hidden 404 for group data; members receive 403 when an owner-only action is known to them. Owners cannot leave/remove themselves before a transactional ownership transfer. Membership uniqueness and the one-owner filtered index backstop application checks under races.

Invitation tokens use 32 random bytes and URL-safe encoding. Only SHA-256 hashes are stored; raw tokens are returned once and excluded from audit/log data. Links place the token in a URL fragment so it is not sent in HTTP request targets, and Angular clears the fragment immediately after reading it. Preview and join use separate authenticated, antiforgery-protected POST requests; preview never creates membership. Unknown, expired and revoked tokens share the same non-disclosing response. Auth and invitation endpoints are rate-limited per client IP and return ProblemDetails with HTTP 429.

Chat read/send/subscribe authorization is checked server-side against `Groups.Contracts`; route guards are not trusted. Mutations use antiforgery and a per-user/IP rate limit, and the hub endpoint is authenticated and rate-limited. Message bodies are never written to application logs. Angular renders text and emoji only through interpolation, not HTML. Sticker messages store only one code from a server-owned catalog; arbitrary URLs, HTML, data URIs and unknown codes are rejected in Application and Domain before persistence. Membership leave/removal publishes a contract after the Groups commit and removes existing connections from the SignalR group; a subsequent subscribe is denied.

Events checks current membership through `Groups.Contracts` before every list/detail/mutation. Group outsiders and former members receive a hidden 404; creator status never bypasses current membership. Creator or current owner is required for edit/confirm/cancel. Mutations use antiforgery, user text is rendered through Angular interpolation, and event descriptions are not logged. RSVP history remains in the Events schema after a member leaves and is returned to current members with `isCurrentMember=false`. A PostgreSQL row lock serializes RSVP with status transitions so the `Open`-only rule holds under concurrency.

There is intentionally no email confirmation, password-reset endpoint or fake “email sent” UI because no email provider is configured. Campfire is therefore suitable only for controlled/private registration at this stage. Before opening registration broadly, add a real provider, verified-email flow, recovery flow, abuse controls and operational support.

Werewolf is server-authoritative. REST/hub entry points require the Identity cookie, every HTTP mutation requires antiforgery and the module rate limit, and room participation is rechecked in Infrastructure. A SignalR connection that changes rooms is removed from its old group/connection registry before the new membership check, preventing retained cross-room subscriptions. Role rows, night targets, votes and recipient-scoped events never appear in another player's projection or SignalR payload. Dead players, spectators, wrong roles, stale/out-of-order phases and actions after the server deadline are rejected. Action/vote IDs and database uniqueness prevent duplicate processing under retries; an ID reused with a changed payload or in a later phase returns 409.

LiveKit credentials remain server configuration. The browser receives only a short-lived token for an opaque phase-specific room with microphone-only publish sources and derived subscribe/publish grants. Night public voice is unavailable; only living Wolves can receive the Wolves channel, and optional dead voice is isolated. Phase changes and host moderation close the old LiveKit room server-side, so hiding a browser control is not the security boundary. Campfire does not enable audio recording or use voice for model training.

Stranger Chat uses a separate 256-bit opaque guest credential in a Secure-on-HTTPS, HttpOnly, SameSite=Lax cookie. Only its SHA-256 hash is persisted; it is absent from URLs, response bodies, browser storage and logs, and public session metadata does not expose the internal guest-session ID. Identity claims are never accepted as guest authority: every guest REST command/query independently verifies the guest credential and conversation participation. SignalR resolves the active conversation through `ISender` and the same Application/Infrastructure authorization path, and its handshake is rate-limited. The selected gender and matching preference are short-lived guest-session data under the existing 24-hour retention policy; neither value is logged, added to an account profile nor disclosed to the matched peer. Matching enforces preferences mutually on the server, so a client cannot force an incompatible pairing by changing UI state. Reporting is idempotent per reporter/conversation, immediately ends an active conversation and notifies both live subscribers; block/report results do not disclose enforcement details. Angular uses text interpolation, URLs are rejected, and the UI exposes end, block and report actions. The product is pseudonymous rather than absolutely anonymous and requires explicit 18+ confirmation.

The local Compose PostgreSQL port binds only to `127.0.0.1`; production PostgreSQL/RDS must remain private and must never be exposed by a public security group. The web/static-file edge must mirror the frontend-relevant security headers because the API can secure only responses that it serves.
